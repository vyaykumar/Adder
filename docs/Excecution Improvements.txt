Applying the C++26 std::execution (sender/receiver) paradigm to the RDMA project described in the provided document completely transforms how the asynchronous network events and CPU compute phases are orchestrated.
The project strictly mandates using C++23 and enforces severe hot-path constraints: no exceptions, no virtual calls, and no heap memory allocation during the timed sections. Because the sender/receiver model builds completely static, zero-allocation state machines at compile time, it perfectly satisfies these rules while eliminating callback spaghetti.
Here is how you can upgrade the specific deliverables using std::execution (via a C++23 reference library like stdexec):
1. Upgrade shared/busy_poll.h to an rdma::cq_scheduler (D1)
The Current State: The project relies on a busy-poll loop to check the Completion Queue (CQ). This intertwines the network polling logic directly with the application control flow.
The std::execution Upgrade:
 * Build a custom rdma::cq_scheduler.
 * Instead of manually posting a work request and spinning in a while loop, you wrap ibv_post_send and ibv_post_recv into a custom Sender.
 * The cq_scheduler runs an inline polling loop that automatically calls set_value on the receiver when the corresponding ibv_wc (work completion) arrives from the hardware.
 * Benefit: Your ping-pong loop becomes a clean chain of asynchronous tasks: post_send() | ex::then(process_cqe) | ex::let_value(post_recv).
2. Pipelined Ring All-Reduce Graph (D2)
The Current State: The scatter-reduce phase requires a node to receive a chunk, add it to local data, and send it to the next node. Doing this sequentially wastes network bandwidth during the CPU addition phase.
The std::execution Upgrade:
You can use std::execution to pipeline the CPU computation and RDMA network transfers seamlessly across different hardware execution contexts without locks.
 * Map a pinned CPU core to a cpu_scheduler (for the vector addition) and the RDMA CQ to the rdma_scheduler.
 * Express the N-1 steps of the ring all-reduce as a continuous sender pipeline using ex::transfer:
// Conceptual pipeline for one chunk in the scatter-reduce phase
auto process_chunk = rdma_recv_sender(chunk_k)
    | ex::transfer(cpu_scheduler)           // Switch to CPU core to do math
    | ex::then(simd_vector_add)             // Vector add the chunk
    | ex::transfer(rdma_scheduler)          // Switch back to network context
    | ex::then(rdma_send_sender(chunk_k));  // Forward to the next ring node

 * Use ex::when_all(process_chunk_1, process_chunk_2, ...) to keep multiple chunks in flight concurrently, automatically maximizing the pipeline bandwidth and getting closer to the theoretical minimum data movement.
3. Straggler Mitigation via Sender Cancellation (D3)
The Current State: The straggler component detects a slow node using an exponential moving average and requires a complex TCP side-channel synchronization using epochs and start rounds to reassign chunks.
The std::execution Upgrade:
The sender/receiver model has a built-in cancellation channel (set_stopped). You can upgrade the straggler mitigation by using timeout adaptors and explicit cancellation trees.
 * Wrap the expected chunk processing time in an ex::stop_when adaptor tied to a timer or a variance threshold monitor.
 * If a chunk operation exceeds the 20x latency threshold for 3 consecutive rounds, the stop_when adaptor triggers the set_stopped signal.
 * This immediately aborts the in-flight pipeline without crashing the program, allowing the let_stopped adaptor to catch the cancellation and cleanly pivot execution into the new schedule (shifting chunks to fast nodes) without needing a heavy TCP epoch barrier.
4. Meeting the Strict C++ Hot-Path Rules
The project requires that the polling loop and send path avoid exceptions, virtual calls, and heap allocations.
 * No exceptions: Senders use the set_error channel for failures (like ibv_modify_qp or CQ errors), bypassing C++ exception unwinding entirely. You handle RDMA errors cleanly via the ex::let_error pipeline adaptor.
 * No heap allocation / virtual calls: Senders are composed via C++ templates. When you call ex::connect(sender, receiver) and ex::start, the entire asynchronous state machine is allocated as a single, contiguous block on the stack (or pre-registered in the guarded_memory_pool.h). There are zero type-erased std::function objects and zero virtual function dispatches.
